AsobiAgent (アソビ・エージェント)

LINEグループに入れるだけ。日程 → 集合駅 → お店 → 予約の準備まで、AIが段取りして、決めるのはみんな。

✨ Gemini（Vertex AI）

会話から日時と希望を読み取り、グループの好みに合わせて、お店ごとの推薦理由を一言で書く。

🚇 駅すぱあと API（MCP）

範囲探索1回で全員の所要時間。一番遠い人の移動が最短になる、公平な集合駅を選ぶ。

💬 LINE（Flex・LIFF）

アプリもアカウント登録も不要。カレンダーとボタンで、全員タップだけで参加できる。

課題

友だちとの予定は、決めるまでがいちばん大変

😫 何十往復のLINE

「いつ空いてる？」「どこから来る？」「何食べたい？」。日程・場所・お店の調整が、毎回ひとりの幹事に集中する。

⚖️ 移動の不公平

集合場所は幹事の近くで決まりがち。「自分だけ片道1時間」「乗り換え3回」という不満が残る。

🗣️ 声の大きい人で決まる

全員の好みを聞くのは面倒。苦手な料理の人がいても、気づかないまま予約してしまう。

🗣️ 発表用スクリプト

「友だちとご飯に行くとき、日程・場所・お店を決めるまでに、LINEで何十往復もします。移動時間は不公平になりがちで、好みも聞ききれません。その負担を、グループに入るエージェントが引き受けます。」

自律性・エージェントらしさ

状況を見て動く、4つのエージェント

Agent 1 · Gemini

📅 日程・希望

雑談から日時と希望を決まった項目に読み取る。全員が○△×を付けたら自分で締め切り、最有力の日でプランを始める。

Agent 2 · 駅すぱあと

🚇 公平な集合駅

範囲探索1回で、全員が行ける駅と各自の平均所要時間を取得。一番遠い人 → 差 → 平均の順で選ぶ。

Agent 3 · Gemini

🍽 お店選び

ホットペッパーとTime Outから、全員の「好き」を重ねて6軒。苦手な料理と、予定時刻に閉まる店は外す。理由はGeminiが一言で（✨）。

Agent 4 · 人が決める

📞 予約の準備

日付・人数入りの電話台本、発信ボタン、予約ページ。フォーム入力エージェント（Playwright＋Gemini）はデモ用フォームだけ。

🧭 次の一手をボットが判断：状態に合わせてボタンを出し分ける
🔎 日程が決まり駅がそろえば、自動で検索へ
🔁 「和食がいい」と送れば、条件を読み直して探し直す
🗣️ 発表用スクリプト

「4つのエージェントが、グループの状況を見ながら次の一手を決めます。全員が日程に答えたら締め切り、全員の駅がそろえば検索を始め、好みに合うお店をGeminiが説明します。」

管理・制御、可観測性、セキュリティ

自律するけど、暴走しない

🧭 人が最後に決める・使いすぎない

  • 📞AIは電話も予約確定もしない。台本と発信ボタンを用意するだけ
  • 🔑招待制。1グループ1軒・検索3回・7日・10人まで
  • 🧾1日の上限（LLM 300・検索 100・Places 30）と予算アラート
  • 🛡Webhookは署名検証。重複イベントと古いボタンは無視

🔎 LLMを信じすぎない・見える化

  • 🧱LLMは候補IDから選び、決まった項目を埋めるだけ。実在を確かめてから使うので、指示を注入されても店や操作を作れない
  • 🔁Vertex AI → GMI Cloud → ルールの3段構え。AIが止まってもグループは止まらない
  • 📈ログに会話の中身は残さない。記録するのはイベントの種類、どのモデルが何秒で答えたか、エラー
  • 📊管理者は /stats で今日の利用量を確認
🗣️ 発表用スクリプト

「エージェントは自律して動きますが、電話や予約の確定はしません。LLMは決められた候補の中から選ぶだけなので、プロンプトインジェクションでお店を作ることはできません。上限とフォールバックで、止まらず、使いすぎません。」

プライバシー

呼ばれるまで読まない、決まったら消す

🙈 呼ばれるまで読まない

待機中のトークは読まずに捨てる。募集中も、参加した人のメッセージだけ。

🔐 IDは匿名化

LINEのユーザーIDとグループIDは、HMACで変換してから保存。

🧹 自動で消える

会話は検索後、名前と投票は決定時に削除。プラン7日・日程14日・プロフィール180日で自動削除。いつでも自分で削除可。

🤐 Geminiに名前を渡さない

モデルに渡すのは「焼肉好き2人」のような人数だけ。会話は「参加者1」のように番号で。

🗣️ 発表用スクリプト

「呼ばれるまでトークは読みません。IDは匿名化し、お店が決まったら名前と投票を消して、ボットはグループを退出します。」

駅すぱあと API（MCP）

範囲探索1回で、公平な集合駅

🛡️ 時刻表を使わない機能だけ

  • ✅ ダイヤ探索（時刻指定）は不使用
  • ✅ ekispert_api_search_ranges を1回呼ぶだけで、全員分の平均所要時間
  • ✅ 駅名は get_stations、現在地は get_stations_from_geo で照合（90日キャッシュ）

⚖️ 公平な選び方

① 一番遠い人の移動時間が最短 → ② 同じなら差が最小 → ③ それも同じなら平均が最小。

横浜 42分 ・ 吉祥寺 39分 ・ 中目黒 40分 ・ 柏 44分
➔ 集合駅「秋葉原」：最大44分・差は5分（駅すぱあとの実際の結果）
🗣️ 発表用スクリプト

「時刻指定のダイヤ検索は使っていません。範囲探索を1回呼ぶだけで、全員が行ける駅と所要時間が分かります。一番遠い人の負担が最も小さい駅を選びます。」

実装品質と拡張性

小さく動かして、そのまま広げられる

☁️ サーバーレス

Cloud Run（使わないときは0台）、Firestore（TTL）、Secret Manager、Cloud Build。秘密情報はコードに置かない。

🧪 自動テスト

グループの一連の流れ、上限、削除、フォールバック、審査用コードなど 79 件。

💴 コストが読める

1回の検索でGeminiは1〜2回。返信だけで動くのでLINEのプッシュ通数は0。上限で青天井にならない。

🔧 広げやすい

上限は環境変数で調整。Time Outの都市を足せば東京以外にも。予約の手段も差し替えられる。

実際の友だちとテスト済み：日程調整から集合駅、お店の決定、電話の台本まで、LINEの中だけで完了。テストで見つかった問題（日付が台本に入らない、次に押すボタンが分からない）はその場で修正。

🗣️ 発表用スクリプト

「Cloud Runで動き、使わないときは0台になります。上限があるのでコストも読めます。実際に友だちと使ってみて、出てきた問題はすぐに直しました。」
